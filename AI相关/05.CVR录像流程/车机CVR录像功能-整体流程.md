# 车机系统 CVR 录像功能 — 整体流程

> 最后更新：2026-07-02

---

## 一、什么是 CVR

**CVR（Cockpit Video Recorder / Continuous Video Recording）** 即车载座舱录像系统，集成在车机（IVI, In-Vehicle Infotainment）系统中，持续录制车辆周围和/或座舱内部的视频、音频、位置及传感器数据。通俗讲就是 **"车机内置行车记录仪"**，但比独立行车记录仪与车机系统耦合更深。

典型应用场景：
- 行车录像（前后双摄 / 360° 环视）
- DMS（驾驶员监控系统，疲劳/分心检测）
- 停车监控（碰撞/移动侦测触发录像）
- 紧急事件锁定（碰撞自动保存，不被循环覆盖）
- 云端同步（4G/WiFi 上传关键片段）

## 二、整体系统架构

从底向上分为 **五层**：

```
┌──────────────────────────────────────────────────┐
│                ⑤ 应用层 (Application)              │
│   QT / Android GUI：预览、回放、设置、文件管理      │
├──────────────────────────────────────────────────┤
│              ④ 框架服务层 (Framework)               │
│   消息管理、IPC 通信、服务注册、OTA 升级            │
├──────────────────────────────────────────────────┤
│            ③ 多媒体中间件层 (Middleware)            │
│   GStreamer / FFmpeg / V4L2 直接采集              │
│   视频编码(H.264/H.265)、音频编码(AAC)             │
│   文件封装(MP4/TS)、流媒体推送                      │
├──────────────────────────────────────────────────┤
│             ② Linux 内核层 (Kernel)                │
│   V4L2 框架、ALSA 音频、DMA-BUF 零拷贝              │
│   DRM/KMS 显示、文件系统(ext4/FAT32)               │
│   Camera Sensor 驱动、G-Sensor 驱动                │
├──────────────────────────────────────────────────┤
│                ① 硬件层 (Hardware)                  │
│   SoC(ARM Cortex-A)、Camera Sensor(MIPI CSI)      │
│   硬件编码器(H.264/H.265)、G-Sensor、GPS           │
│   存储(eMMC/SD卡)、电源管理(超级电容)              │
└──────────────────────────────────────────────────┘
```

## 三、各层详细流程

### 3.1 硬件层 — 核心器件选型

| 器件 | 常见型号 | 作用 |
|------|---------|------|
| **主 SoC** | 海思 Hi35xx、RK3576、Ambarella H22、NXP i.MX8 | 系统主控，集成 ISP + 硬件编码器 + NPU |
| **图像传感器** | IMX335、IMX415、OV4689 | MIPI CSI-2 接口，输出 RAW/YUV 数据 |
| **硬件编码器** | SoC 内置 H.264/H.265 编码器 | 实时编码，CPU 零开销 |
| **G-Sensor** | 加速度传感器（I2C/SPI） | 碰撞检测、急刹车/急转弯触发 |
| **存储** | eMMC / SD 卡（Class 10 以上） | 录像文件存储 |
| **电源管理** | 超级电容 / 备用电池 | 断电时完成文件收尾，防止损坏 |
| **GPS/北斗** | UART 接口模块 | 记录行车轨迹、速度 |

### 3.2 Kernel 层 — 驱动与框架

#### 3.2.1 V4L2 视频采集框架

Linux 标准的视频采集接口，CVR 最核心的驱动层。标准采集流程（8 步）：

```
① open("/dev/video0")          — 打开摄像头设备
② VIDIOC_QUERYCAP              — 查询设备能力（是否支持采集、叠加等）
③ VIDIOC_S_FMT                — 设置格式（分辨率、像素格式如 NV12/YUYV）
④ VIDIOC_REQBUFS              — 申请内核缓冲区（通常 4~8 个）
⑤ mmap()                      — 将内核缓冲区映射到用户空间（零拷贝基础）
⑥ VIDIOC_QBUF                 — 将缓冲区放入采集队列
⑦ VIDIOC_STREAMON             — 启动视频流
⑧ 循环 VIDIOC_DQBUF → 处理数据 → VIDIOC_QBUF  — 取帧→编码→还回
```

关键要点：
- 使用 **mmap** 方式（而非 read/write），避免内核态→用户态拷贝
- 多摄像头时每个摄像头对应独立 `/dev/videoN`
- 像素格式通常选 **NV12**（硬件编码器普遍支持）

#### 3.2.2 DMA-BUF 零拷贝优化

**这是车机多摄像头系统的关键优化点**。传统方案每帧数据要拷贝 5 次以上，对于 4 路 1080P@30fps 摄像头，每秒有 ~200MB 的数据搬移开销。

```
传统方案（❌）：
  V4L2 buf → [拷贝]→ CPU buf → [拷贝]→ Encoder → [拷贝]→ Display
  共 5 次全帧拷贝，延迟 ~300ms

DMA-BUF 方案（✅）：
  V4L2 DMA-BUF fd → RGA(格式转换) → DRM Overlay Plane
  共 0 次拷贝，延迟 ~100ms
```

原理：通过 `VIDIOC_EXPBUF` 导出 DMA-BUF 文件描述符(fd)，各模块（编码器、RGA、显示）通过同一个 fd 访问同一块物理内存，无需拷贝。

#### 3.2.3 ALSA 音频采集

```
PCM 设备打开 → 设置参数(采样率/位深/通道) → 循环 snd_pcm_readi() 取音频帧
```

#### 3.2.4 ISP Pipeline（图像信号处理）

现代车载 SoC 内置硬件 ISP，处理链如下：

```
RAW 数据输入 → 3A(AE/AWB/AF) → HDR 合成 → LDC 畸变校正
            → 3D MCTF 降噪 → EIS 电子防抖 → 旋转/镜像 → YUV 输出
```

### 3.3 多媒体中间件层 — 音视频处理

#### 3.3.1 两套主流方案对比

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|---------|
| **GStreamer** | 插件化、灵活、社区活跃、KVS 云同步 | 调度开销大、内存占用高 | 快速开发、需要流媒体推送 |
| **V4L2 + 硬件编码器 API** | 延迟低、资源占用小 | 开发工作量大、不灵活 | 资源受限、高实时性要求 |

#### 3.3.2 GStreamer Pipeline 示例

```bash
# 典型 CVR 录制 pipeline：采集 → 编码 → 封装 → 存文件
gst-launch-1.0 \
  v4l2src device=/dev/video0 ! \
  video/x-raw,format=NV12,width=1920,height=1080,framerate=30/1 ! \
  v4l2h264enc ! \
  h264parse ! \
  tee name=t \
    t. ! queue ! mp4mux ! filesink location=/storage/cvr_$(date).mp4 \
    t. ! queue ! kvssink stream-name="cvr-live"  # 可选的云推流

# 音视频合路录制
gst-launch-1.0 \
  v4l2src device=/dev/video0 ! video/x-raw,format=NV12 ! v4l2h264enc ! h264parse ! mux. \
  alsasrc device=hw:0    ! audio/x-raw,rate=16000  ! voaacenc   ! aacparse  ! mux. \
  mp4mux name=mux ! filesink location=/storage/cvr_av.mp4
```

#### 3.3.3 视频编码关键参数

| 参数 | 推荐值 | 说明 |
|------|--------|------|
| **编码格式** | H.264（主流）/ H.265（高压缩比） | 必须硬件编码 |
| **分辨率** | 1920×1080（前摄）/ 1280×720（内摄） | 根据 Sensor 和需求调整 |
| **帧率** | 30fps（正常）/ 15fps（停车监控） | 平衡流畅度与存储 |
| **码率** | 4~8 Mbps（1080P） | 平衡画质与存储空间 |
| **GOP** | 30（即 1 秒一个关键帧） | 影响回放 seek 精度 |
| **音频编码** | AAC（LC profile） | 16kHz 采样率，单声道，32kbps |

### 3.4 框架服务层 — IPC 与消息管理

车机系统中，CVR 通常作为独立进程运行，需要与上层 GUI 和其他车机服务通信。

```
┌─────────┐    Socket/消息队列    ┌──────────────┐
│ QT GUI  │ ◄──────────────────► │  CVR Service  │
│ (显示层) │     IPC 通信          │  (后台服务)    │
└─────────┘                       └──────┬───────┘
                                         │
                                    内部线程通信
                                         │
                    ┌────────────────────┼────────────────────┐
                    │                    │                    │
               ┌────▼────┐       ┌──────▼──────┐      ┌─────▼─────┐
               │ 视频采集 │       │  编码存储    │      │ 事件监测   │
               │ 线程     │       │  线程        │      │ 线程       │
               └─────────┘       └─────────────┘      └───────────┘
```

通信机制：
- **跨进程**：Unix Domain Socket / D-Bus / Binder（Android）
- **跨线程**：互斥锁 + 条件变量 / 消息队列
- **心跳机制**：GUI 与 Service 间保持心跳，断连自动重连
- **命令优先级**：紧急锁存 > 参数设置 > 文件查询

### 3.5 应用层 — 用户交互

GUI 框架选择：
- **Android 车机**：Java/Kotlin + SurfaceView/TextureView 预览
- **嵌入式 Linux 车机**：QT5（主流）/ LVGL / 直接操作 DRM Framebuffer

主要功能界面：
| 模块 | 功能 |
|------|------|
| **实时预览** | 单路/多路视频实时显示 |
| **录像控制** | 手动启停、分辨率切换、时长设置 |
| **文件管理** | 录像文件列表、回放、删除、导出 |
| **紧急事件** | 锁定文件列表、碰撞事件查看 |
| **设置** | 循环时长、G-Sensor 灵敏度、停车监控开关 |
| **设备状态** | 存储空间、GPS 信号、各模块工作状态 |

## 四、核心功能模块详解

### 4.1 循环录制（Loop Recording）

**CVR 最核心的功能**。存储空间有限，需要不断覆盖最早的录像。

```
存储分区策略：
┌────────────────────────────────────────────────┐
│  CVR 存储空间（如 32GB）                         │
├────────────┬───────────────────────────────────┤
│  保护区     │  循环区                            │
│  (2GB)     │  (30GB)                            │
│  紧急锁存   │  正常循环录像                       │
│  不可覆盖   │  空间满时覆盖最旧文件                │
└────────────┴───────────────────────────────────┘
```

循环逻辑：

```
1. 初始化：分配 N 个固定时长片段（如 1 分钟/个），形成环形缓冲区
2. 当前片段写满后：
   a. 关闭当前文件，完成封装
   b. 指针移到下一个槽位
   c. 如果槽位有旧文件 → 删除（覆盖）
   d. 创建新文件，继续写入
3. 遇到紧急事件 → 将当前片段移到保护区，跳过此槽位
```

实现要点：
- **文件命名**：`YYYYMMDD_HHMMSS_序号.mp4`，便于检索排序
- **片段时长**：通常 1 分钟（平衡文件大小和丢失风险）
- **存储检查**：每个循环周期检查剩余空间，低于阈值时告警
- **断电保护**：使用 ext4 文件系统（journal 机制），断电后文件自动修复

### 4.2 紧急事件锁定（Emergency Lock）

通过 G-Sensor 检测碰撞/剧烈震动，自动保护当前录像不被覆盖。

```
触发条件：
├── G-Sensor 加速度突变（碰撞检测）
├── 急刹车（减速度 > 阈值）
├── 急转弯（角速度 > 阈值）
└── 用户手动触发（按钮/语音）

处理流程：
1. G-Sensor 中断 → 读取加速度值
2. 判断是否超过阈值
3. 如果是紧急事件：
   a. 将当前正在写入的片段标记为"锁定"
   b. 写入完成后移动到保护区
   c. 同时锁定前 N 秒和后 M 秒（保证事件完整）
   d. 通知 GUI 弹出提示
   e. 可选：自动上传云端
```

G-Sensor 阈值设计（需实车标定）：

| 事件类型 | 典型阈值 | 锁定范围 |
|---------|---------|---------|
| 轻度碰撞 | ±2g | 前10s + 后10s |
| 中度碰撞 | ±4g | 前15s + 后15s |
| 严重碰撞 | ±8g | 前20s + 后20s |
| 急刹车 | X轴 -0.5g | 前10s + 后5s |

### 4.3 停车监控（Parking Monitor）

车辆熄火后，CVR 进入低功耗待机模式，侦测到异常时唤醒录制。

```
停车监控流程：
1. 车辆熄火 → ACC OFF 信号 → CVR 进入休眠模式
2. 低功耗侦测：
   a. G-Sensor 震动侦测（碰撞）
   b. 可选：视频移动侦测（画面变化）
3. 触发后：
   a. 唤醒主控，快速启动录制
   b. 录制 30s~60s 短视频
   c. 存入独立"停车监控"目录
4. 电量保护：电瓶电压低于阈值 → 完全关机
```

### 4.4 音视频同步

音频和视频是独立线程采集的，需要精确对齐时间戳。

```
同步策略：
1. 以系统时钟（CLOCK_MONOTONIC）为基准
2. 视频帧：记录采集时刻的 PTS（Presentation TimeStamp）
3. 音频帧：同样记录 PTS
4. 编码时：PTS 写入编码帧
5. 封装时：以视频为基准，调整音频 PTS 偏移

多路摄像头同步：
- 软同步：系统时间戳对齐（误差 < 50ms，可接受）
- 硬同步：由同一时钟源（如 PCLK）驱动多路 Sensor（误差 < 1ms）
```

### 4.5 多线程架构

```
主线程（Main Thread）
  │
  ├── 视频采集线程 ─── 环形缓冲区(V) ──┐
  │                                    │
  ├── 音频采集线程 ─── 环形缓冲区(A) ──┤
  │                                    │
  ├── 编码/存储线程 ◄──────────────────┘
  │      │
  │      ├── 音视频编码（硬件加速）
  │      ├── 封装写入文件
  │      └── 循环管理 / 紧急锁存
  │
  ├── G-Sensor 监测线程 ─── 事件判断 → 通知编码线程
  │
  └── IPC 通信线程 ─── 响应 GUI 指令，上报状态
```

线程同步机制：
- **生产者-消费者模型**：采集线程（生产者）→ 环形缓冲区 → 编码线程（消费者）
- **互斥锁**：保护共享缓冲区
- **条件变量**：采集线程有新帧时通知编码线程；编码线程消费后通知采集线程可继续写入
- **信号量**：管理缓冲区空闲/已用槽位

## 六、关键技术决策总结

| 决策点 | 推荐选择 | 原因 |
|--------|---------|------|
| **多媒体框架** | GStreamer（开发阶段）/ 裸 V4L2+编码器（量产阶段） | GStreamer 快速迭代，裸 API 省资源 |
| **编码方式** | 硬件编码（必选） | 4 路 1080P 软件编码 CPU 无法承受 |
| **零拷贝方案** | DMA-BUF + DRM Overlay | 延迟从 300ms → 100ms，CPU 占用大幅降低 |
| **文件容器** | TS（流式）/ MP4（存储） | TS 断电安全更好；MP4 兼容性更好 |
| **文件系统** | ext4 | 带 journal，断电自动修复；FAT32 有 4GB 限制 |
| **像素格式** | NV12 | 硬件编码器普遍支持，Y 和 UV 分离方便处理 |
| **预览方案** | DRM Overlay Plane | 零拷贝直接显示，不走 X11/Android Surface |
| **音频编码** | AAC-LC | 体积小、音质可接受、硬件编码支持广泛 |
| **AI 推理 (ADAS/DMS)** | NPU（SoC 内置） | 多路推理 CPU 撑不住，NPU 功耗更低 |

## 七、从零搭建的推荐路径

如果你是第一次做车机 CVR，建议按以下顺序渐进式搭建：

```
第 1 步：单路摄像头采集 + 显示
  ├── 搞定 V4L2 驱动和基本采集流程
  ├── 在屏幕上实时预览（DRM/Framebuffer）
  └── 验证：能看到实时画面

第 2 步：硬件编码 + 文件存储
  ├── 接入硬件 H.264 编码器
  ├── 实现 MP4/TS 封装和写入
  └── 验证：能生成可播放的录像文件

第 3 步：循环录制
  ├── 实现分段录制（1 分钟/段）
  ├── 环形覆盖逻辑
  └── 验证：存储满后自动覆盖最老文件

第 4 步：音频集成
  ├── ALSA 音频采集
  ├── AAC 编码 + 音视频同步
  └── 验证：录像带声音，音画同步

第 5 步：事件检测
  ├── G-Sensor 驱动 + 数据读取
  ├── 碰撞检测算法 + 紧急锁存
  └── 验证：拍打设备能触发锁定

第 6 步：多摄像头扩展
  ├── 第 2~4 路摄像头接入
  ├── 多路同步处理
  └── 验证：多路同时录制不卡顿

第 7 步：GUI + 完整功能
  ├── QT 界面开发
  ├── IPC 通信（GUI ↔ CVR Service）
  ├── 回放、设置、文件管理
  └── 验证：完整产品体验

第 8 步：可靠性优化
  ├── 断电保护测试
  ├── 长期稳定性测试（72 小时+）
  ├── 高低温测试
  └── 性能优化（DMA-BUF 等零拷贝方案）
```

## 八、常见踩坑点

1. **V4L2 缓冲区不够用**：至少 4 个缓冲区，多路摄像头时适当增加，否则会丢帧
2. **没有做断电保护**：用 FAT32 或没做 MP4 moov atom 前置处理的，断电后文件损坏无法播放。必须用 ext4 + 定期 flush moov atom
3. **音视频不同步**：音频和视频 PTS 各自以独立时钟为基准，没做偏移校正
4. **循环覆盖删除正在读取的文件**：回放时文件被覆盖，加引用计数保护
5. **高低温下 SD 卡写速下降**：实车验证，选择车规级存储
6. **G-Sensor 阈值没标定**：实车路测标定，否则误触发或漏触发
