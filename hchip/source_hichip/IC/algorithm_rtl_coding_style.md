# 算法类 RTL 通用 Coding Style

## 1. 文档目的

本文档给出一版更通用的算法类 RTL 编码风格，适用于：

1. 压缩 / 解压
2. 图像 / 视频像素处理
3. 滤波 / 变换 / 插值
4. 流式统计 / 解析 / 重组
5. 其他以数据通路为核心、带少量控制状态的硬件模块

目标不是规定书写习惯，而是沉淀一套更利于：

1. 综合工具识别
2. 时序闭合
3. 面积和功耗可控
4. Lint 和 Review 可读
5. 后续验证和交接

## 2. 总原则

算法类 RTL 的总原则只有一句话：

把代码写成硬件结构描述，而不是软件执行步骤翻译。

可以进一步拆成 4 条：

1. 数据怎么流，代码就怎么分层。
2. 控制什么时候推进，代码就什么时候更新状态。
3. 长路径要靠结构切段解决，不靠“写短一点”解决。
4. 固定拓扑优先于过程式遍历。

## 3. 适用边界

这份风格特别适合下面这类模块：

1. 输入输出都有明确吞吐边界
2. 存在固定长度样本、窗口、block、CU、tile、packet 或 segment
3. 内部有递推、累加、偏移推进、位流消费或窗口滑动
4. 有少量格式分支，但整体数据通路可复用

如果模块本质上是：

1. 大型寄存器文件
2. 总线协议控制器
3. 明显的多状态事务 FSM

那么仍然可以借鉴本文档，但不能生搬硬套。

## 4. 强制规则

### 4.1 不在可综合 RTL 中使用 `task`

规则：

1. 可综合 RTL 中不使用 `task`。
2. 局部纯组合变换用 `function automatic`。
3. 可复用运算单元优先写成独立子模块。

原因：

1. `task` 容易把硬件结构写成过程式调用。
2. 对综合、Lint、STA、形式验证都不够透明。
3. 子模块、函数、`generate` 更容易反映真实结构边界。

### 4.2 输入输出必须寄存器打拍

规则：

1. 输入数据要先进入寄存器级。
2. 输入控制信号也要和数据一起打拍或明确对齐。
3. 输出数据必须由寄存器保持。
4. 输出 `valid` 必须由寄存器保持。
5. `valid && !ready` 时，输出数据和附属控制必须稳定不变。

原因：

1. I/O 打拍是时序闭合的第一道边界。
2. 便于把接口语义和内部组合深度隔离。
3. 能避免接口级毛刺和跨级对齐错误。

### 4.3 主数据通路不写成软件风格多重循环

规则：

1. 顶层主数据通路避免双重或多重 `for` 循环堆组合逻辑。
2. 不要在一个组合块里一边遍历、一边累计偏移、一边更新结果。
3. 特别是格式解析、payload 抽取、lane 拼接、缓存写回、窗口搬移等关键路径，不要写成软件式扫描。

允许的例外：

1. reset / clear 时的小规模数组清零
2. 非关键路径的小规模 mask 生成
3. 明确会被综合为固定展开的小范围单层循环

### 4.4 固定格式和固定拓扑必须显式展开

规则：

1. 固定位段解析按固定 bit 位置展开。
2. 固定 offset 计算按固定公式展开。
3. 固定 lane / channel / sample 拼接按固定 mux 展开。
4. 缓存写回、窗口选择、payload 取数优先写成固定网络。

原因：

1. 更像真实硬件网络。
2. 综合工具更容易识别为 mux、加法器、移位网络。
3. 后续做时序分析、面积分析、ECO 更容易追踪。

### 4.5 长数学链和递推链必须切段

规则：

1. 递推链、前缀链、累加链、偏移推进链不能整条堆成一拍。
2. 必须按结构边界或数学边界切段。
3. 每段都要有清晰的输入、输出和寄存器切点。

适用场景：

1. predictor / feedback 链
2. 累积 bit offset
3. 多样本顺序重建
4. 多级压缩 / 解压判决
5. 多项组合条件归约

规则重点：

1. 先分段，再优化表达式。
2. 先插 pipe，再做等价保持。
3. 不要把所有功能都塞进一个“万能组合块”。

### 4.6 状态只能在明确的“提交点/退休点”更新

规则：

1. 跨 block 的历史状态只能在当前事务真正完成时更新。
2. 位置计数、窗口推进、行列坐标、历史样本等状态不能提前写。
3. 若存在 backpressure，必须定义唯一的 commit/retire 条件。

原因：

1. 避免状态和数据脱拍。
2. 避免一拍内重复提交或提前提交。
3. 调试时更容易找到唯一生效点。

### 4.7 控制通路和数据通路分开写

规则：

1. 数据通路按“数据怎么流”来组织。
2. 控制通路按“什么时候推进、什么时候保持、什么时候清空”来组织。
3. 不要在一个组合块里同时塞满数据拼接、状态推进和异常处理。

推荐拆法：

1. `function automatic` 负责局部数据变换
2. `always @*` 负责 next-state 或组合控制判断
3. `always @(posedge clk ...)` 负责寄存器更新
4. `generate` 负责固定重复结构

### 4.8 物理资源复用优先于重复造轮子

规则：

1. 有相同结构的运算通道时，优先复用公共 datapath。
2. 物理并行度按最大真实需求定，不按所有模式简单叠加。
3. 模式差异尽量放在顶层映射和控制上，不要为每种模式复制一整套数据通路。

原因：

1. 更省面积
2. 更省扇出
3. 更利于统一验证和维护

### 4.9 位宽、符号、截断必须显式

规则：

1. 关键位宽由 `parameter/localparam` 显式定义。
2. 符号扩展必须显式写出。
3. 截断、拼接、移位、part-select 必须写清楚。
4. 避免依赖隐式扩展、默认 signed 传播和无约束 `integer` 运算。

推荐写法：

1. 用 `logic [W-1:0]` 明确宽度
2. 用 `$signed({...})` 明确符号语义
3. 用 `+:` / `-:` 明确切片边界

### 4.10 写完 RTL 必须跑 lint

规则：

1. 代码写完后必须跑 lint，而不是只做编译或仿真。
2. lint 结果必须至少满足“没有 error”。
3. warning 要尽可能清掉，不能把可修复 warning 长期堆积成默认状态。
4. 若存在暂时无法清掉的 warning，必须能说明原因，并区分是：
   - 工具规则偏保守
   - 结构性不可避免
   - 当前版本暂未处理的真实设计问题

原因：

1. lint 能尽早暴露综合风格问题、可读性问题和潜在 bug 风险。
2. 许多“软件风格 RTL”问题在功能仿真能过，但会先在 lint 阶段暴露出来。
3. 保持低 warning 基线，后续新增问题才容易被识别。

### 4.11 面积优化优先做“结构减法”

规则：

1. 面积优化前先用 map 级或等价的快速综合结果定位热点，不凭感觉猜大头。
2. 优先减少宽数据副本、宽拼接网络、副本寄存器和高扇出控制网络的数量。
3. 跨拍只保存下一阶段真正需要的最小状态，不要为了书写方便长期保存整包 payload 或整段中间结果。
4. 能在局部重新计算的小组合量，优先局部重算，而不是跨多级寄存大宽度快照。
5. 模式差异尽量收敛到窄控制和映射层，不要因为格式不同就复制整条前后处理链。
6. 面积压力明显时，可以接受合理的时分复用或吞吐下降，但必须显式记录吞吐变化和接口影响。

原因：

1. 算法类模块的面积热点经常不在核心数学单元，而在外围缓存、重排、拼接、快照寄存器和控制扇出网络。
2. 宽数据副本和宽 mux/concat 网络很容易在功能正确的前提下面积失控。
3. 先定位真实热点，再做结构减法，通常比先微调局部算术表达式更有效。

## 5. 推荐结构模式

### 5.1 “函数 + generate + stage 寄存器”模式

适用场景：

1. 固定数量通道
2. 固定数量样本
3. 固定格式拆分
4. 固定窗口拼接

推荐方式：

1. 小函数负责局部抽取或编码
2. `generate` 负责固定重复结构
3. stage 寄存器负责切时序

### 5.2 “前半段组合 + 中间寄存 + 后半段组合”模式

适用场景：

1. 单条路径太长
2. 数据有天然中间边界
3. 数学上可分成两个半段

优点：

1. 切点清楚
2. 等价关系容易验证
3. 时序优化更稳定

### 5.3 “请求包 + 元数据包 + 输出包”对齐模式

适用场景：

1. 顶层驱动多个并行子模块
2. 子模块结果返回时需要重新对齐格式信息
3. 输出侧还要支持背压保持

推荐方式：

1. 请求包保存真正送入子模块的数据
2. 元数据包保存需要与子模块输出同拍对齐的附属信息
3. 输出包提供中间保持和最终对外寄存

### 5.4 “固定 chunk / 固定窗口”缓存模式

适用场景：

1. 输入总线宽，消费粒度细
2. 需要按 bit、nibble、byte 或小 chunk 读取
3. 有 head / tail / count 这种滚动消费模型

推荐方式：

1. 缓存按固定 chunk 宽度组织
2. head/tail 分开维护
3. 读取窗口用固定拼接网络
4. 写回用固定比较网络

### 5.5 “最小必要状态保存”模式

适用场景：

1. 多 stage 流水线需要跨拍传递请求信息
2. 数据总线很宽，但后续 stage 实际只用其中少量字段
3. 输出侧还需要支持 backpressure 或重排

推荐方式：

1. 只把后续 stage 真正需要的字段打包进请求寄存器或 metadata 寄存器。
2. 宽 payload 保持单一路径拥有者，避免在多个 stage 各自留一份快照。
3. 需要回放或保持时，优先保持窄索引、模式、长度、offset、delta 等元数据。
4. 输出重排优先局部完成，不要先把全宽结果到处搬运再统一重排。

### 5.6 “先定位面积热点，再决定复用粒度”模式

适用场景：

1. 设计既有并行度，也允许一定吞吐 tradeoff
2. 不确定面积是由算术单元、缓存、重排网络还是接口保持逻辑主导
3. 需要在 `4-way` / `2-way` / `1-way` 或其他复用粒度间做架构选择

推荐方式：

1. 先看快速综合后的层级面积占比，再决定该减并行度还是先减外围逻辑。
2. 若算术单元占比小，优先优化外围宽向量寄存、拼接和重排网络。
3. 若算术单元占比高，再考虑时分复用、共享 datapath 或降低物理并行度。
4. 任何复用策略都要同步检查吞吐、延迟、握手保持和验证复杂度。

## 6. 不推荐写法

下面这些写法通常说明 RTL 正在向“软件实现风格”滑动：

1. 一个超长 `always @*` 里同时做解析、偏移累计、数学递推、结果拼接
2. 多重 `for` 循环嵌套去“扫描”数据结构
3. 用 `task` 模拟“先做 A 再做 B 再做 C”的过程式调用
4. 所有模式各复制一整套通道逻辑
5. 接口直接挂深组合逻辑，不做保持寄存器
6. 状态在中途路径被提前更新
7. 时序问题靠局部改表达式，而不是靠结构切段
8. 为了跨拍方便复制整包宽 payload、整段窗口数据或整组中间结果
9. 宽向量在多个 stage 里重复寄存、重复拼接、重复拆包
10. 在没有面积热点证据前，先去微调局部算术小模块而忽略外围大网络

## 7. 命名建议

命名不要求唯一风格，但要满足“看名字能猜出硬件角色”。

推荐规则：

1. `*_r`
   表示寄存器态
2. `*_nxt`
   表示 next-state 或组合下一拍值
3. `*_w`
   表示组合中间线网
4. `*_cur`
   表示当前周期解析出的组合值
5. `*_in / *_out`
   表示模块边界或阶段边界
6. `s0 / s1 / s2 ...`
   表示流水 stage
7. `valid / ready / fire / push / pop`
   明确采用握手语义命名

## 8. 注释建议

算法类 RTL 的注释不要写成逐行翻译，而应重点解释：

1. 这个 stage 的输入是什么
2. 这个 stage 的输出是什么
3. 为什么在这里切 pipe
4. 这个组合块在整体数据流中的角色是什么
5. 哪些状态只允许在什么条件下更新

最有价值的注释通常是：

1. 模块头注释
2. 端口注释
3. stage/功能块注释
4. 长路径切段原因注释
5. commit/retire 条件注释

## 9. 提交前自检清单

提交前至少回答下面这些问题：

1. 是否在可综合 RTL 中引入了 `task`。
2. 输入和输出是否都已经寄存器打拍。
3. `valid && !ready` 时是否保持稳定。
4. 顶层主数据通路里是否出现软件风格多重循环。
5. 关键解析和拼接逻辑是否已经写成固定拓扑。
6. 长数学链或递推链是否已经切段。
7. 历史状态、位置状态是否只在明确提交点更新。
8. 位宽、符号、截断是否都显式可追踪。
9. 是否优先复用了公共 datapath。
10. 是否已经跑过 lint，并确认没有 error、warning 已尽可能清理。
11. 是否保存了超过下一 stage 实际需要的宽 payload 或大快照寄存器。
12. 宽拼接、重排、mux 网络是否可以进一步局部化或减少副本。
13. 面积优化前是否已经有快速综合热点证据，而不是凭感觉改结构。
14. 这份代码拿给综合或 STA 工程师时，能否一眼看出真实硬件结构。

## 10. 一句话总结

算法类 RTL 的推荐风格是：

固定拓扑、显式切段、接口打拍、状态晚提交、资源可复用、控制与数据分离，并优先通过结构减法控制面积。

只要代码读起来更像一张可综合的结构图，而不是一段过程式算法脚本，方向通常就是对的。
